## 固定目标与组件

| 组件 | 固定值 | 说明 |
|---|---|---|
| Ubuntu | 26.04 LTS | 唯一一等生产 OS |
| Architecture | `linux/amd64` | Compose 和镜像均固定平台 |
| Resource profile | 2 vCPU / 4 GiB RAM / minimum 40 GiB SSD | 40 GiB 是最低支持与历史预算，不是当前 VM 的容量声明 |
| CPython | 3.14.7 | application/operations image runtime |
| PostgreSQL / pgvector | 17.10 / 0.8.6 | pinned base image |
| pgBackRest | 2.59.1 (`2.59.1-1.pgdg12+1`) | PGDG package；`.deb` SHA-256 为 `ecea2337fe53ec1f86d87db21ad46747c7ff898bd877288452b90374e80a6fb9` |
| Redis | 8.2.8 | pinned base image |
| Caddy | 2.11.4 | pinned base image；只由 gateway 暴露 443 |

pgBackRest 2.45 与 PostgreSQL 17 的 control/catalog version 不兼容。PostgreSQL
镜像构建现在从基础镜像已配置的 PGDG 源下载精确版本，先校验上述哈希，再安装
本地 `.deb`；包源仍不是生产镜像或 SBOM 验收证据。
`base-images.lock.json` 的 `verified_at`（2026-08-23）只标记基础镜像 registry
manifest inspection；本轮 pgBackRest `.deb` 哈希校验是补充的包完整性事实，不代表
重新完成生产镜像、SBOM 或发布验收。

M8-001—M8-016 当前在 acceptance manifest 中均为 `NOT RUN`。其中 M8-003、
M8-009、M8-010、M8-011 和 M8-013 有已经通过的支持性静态测试，分别只覆盖部分
secret/mount、磁盘阈值、服务状态投影、reclaimed-export 清理和 runbook fail-closed
边界；它们不分别证明完整 runtime identity、retention/media、logs/alerts/
`/server_status`、age/SSH/SFTP 导出或 fresh Ubuntu runbook 可复现性。

本地测试套件的 `PASS` 只说明所执行的源码契约成立。生产验收时必须在固定候选上重新生成 M8 acceptance manifest，并核对签名
提交和该提交的 CI 结果；不能把旧 M7 manifest、一次性
VM build-check 或局部 static/synthetic test 复用为 M8 requirement acceptance。

2 vCPU、4,100,780,032 B RAM（约 3.82 GiB）、无 swap，根 `ext4` 文件系统总容量

该 VM 已用于 M8 Ubuntu synthetic/operations 验证；上述历史检查未建立 40 GiB 受限卷/配额证据，
当时的自由空间也不足以分配 fresh 40 GiB soak 环境。后续须重新核对实时容量；历史观察不改变
`v1_2cpu_4g_minimum40_target` 契约。除非建立可靠的 40 GiB 受限卷或等价配额模拟并
记录完整 disk-watermark 证据且运行满 24 小时，否则 M8-015 保持
`NOT RUN`/`BLOCKED`。

## 明确未覆盖

- 生产镜像、SBOM、license review、真实 secrets 和 off-host backup target；
- 真实 Telegram update/send、Bot polling、provider 请求和 AUTO；
- 真实 TLS、公网扫描、整机 restore、erasure reconciliation、RPO/RTO；
- 24 小时 2/4/40 workload、宿主重启以及长期资源趋势。

这些项目必须在同一个签名候选和不可变 artifact 上重新执行，结果分别记录为
`PASS`、`FAIL`、`NOT RUN` 或 `BLOCKED`，不能由静态测试或 synthetic fake 代替。
