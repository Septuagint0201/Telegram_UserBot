# M5 Compatibility Set

本文固定M5 Media与Context Contract的实现、测试和安全边界。M5只允许synthetic图片、fake Telegram/provider和disposable PostgreSQL/Redis；真实私聊图片、真实Telegram Session、provider credential、AUTO发送和部署继续为`NOT RUN`。

## 固定组件与限制

| 组件 | 固定版本或默认值 | M5用途 |
|---|---|---|
| CPython | 3.14.7 | 本地与GitLab执行环境 |
| Pillow | 12.3.0，hash-lock | JPEG/PNG/WebP完整解码、像素限制与metadata-free provider copy |
| PostgreSQL / pgvector | 17.10 / 0.8.6 | Context policy/manifest/preview的durable truth |
| 图片摄取 | 20 MiB、40 MP、单边16384 px、30秒、并发1 | 下载前声明限制和下载后magic/MIME/完整解码双重校验 |
| Media volume | private 0700、10 GiB | original默认30天、provider copy默认24小时；不进入backup |
| Context | 24,000 token默认上限 | 受model window、output reserve、5%/1024安全余量、图片reserve约束 |

Alembic head为`0006_m5_media_context`。M5新增11张表，并为capability snapshot增加image count/byte/token/auto-equivalence字段；迁移链必须验证empty→head、head→base→head以及`0001`至`0005`各支持点→head，并执行`m1_roles.sql`至`m5_roles.sql`。

## Media contract

只有M3标记为download eligible的Telegram photo与image MIME document可以通过`TelegramImageSource`流式进入`ImageIngestor`。下载由应用解析的message/revision/position identity定位，消息正文不能提供URL或文件路径。JPEG、PNG、WebP以实际解码格式为准；声明MIME不一致、多帧动画、截断、未知格式、超字节、超像素、超边长、解码炸弹或超时均fail closed。Voice、audio、video、video note、非图片document与sticker继续只存metadata。

`PrivateMediaStore`仅接受validated bytes，以opaque account/hash/object key和0600原子临时文件写入app-owned 0700 namespace，写后用hash重验。Provider copy经过EXIF orientation规范化和重新编码，不继承metadata。`MediaRepository`持久化pending→ready/rejected和30天/24小时expiry；清理只领取过期且无message reference的ready对象。M8再接入70/80/90/95%磁盘水位和最终Operations调度。

## Context contract

Main AI预算公式为`min(policy.max_input_tokens, model_context - max_output - max(1024, 5% model_context))`。图片使用`detail=auto`且默认每张预留2048 token；required current turn、album和图片不截断，移除全部可选层后仍超限则以稳定错误阻止run。

Structured memory按显式feature权重、novelty和稳定ID排序；semantic只在一个active embedding space内对固定候选做exact distance rerank。Recent优先于同source的structured/summary/semantic呈现。所有非人工trusted instruction内容进入带source/trust label的user/assistant data boundary；正文中的`SYSTEM:`、XML、Markdown、URL、path或tool名称不会改变role、权限或执行行为。

Manifest不复制正文，只保存typed ordered source ID/revision、trust、reason、score、token/image estimate、policy/config版本、prompt/capability snapshot hash、content/render hash、source revision vector与manifest hash。持久化前再次核对调用方提供的prompt/capability hash与manifest完全一致。M5固定`trusted_instruction`、`message_revision`、`media_object`、`memory_version`和`summary_version` discriminator；后两类的数据库外键与受控preview读取在M6派生表落地时补上。同一可用source snapshot可确定性重建；缺失、编辑、删除或redaction导致source identity/hash不一致时fail closed。

Responses和Chat Completions使用受信data URL并显式映射`detail=auto`；Messages使用base64 media source，并且只有capability snapshot明确声明provider default等价于automatic detail时才允许。任何含图请求都必须提供validated capability snapshot并先检查数量与字节限制；Telegram CDN URL或消息正文URL不会直接交给provider。

## Control与隐私边界

`/context <opaque-target>`只显示manifest短ID、purpose/role、总预算、layer计数/token、image count、freshness、omission和版本，不显示message/memory正文、API key或provider body。

`/context_preview`只允许allowlisted管理员私聊，先绑定exact manifest/source vector创建五分钟一次性token；token只通过Confirm按钮的非文本callback传递，不出现在Bot消息正文或可手输命令参数。CAS消费后再次由受限rebuilder验证source未edit/delete/redact，在内存构造synthetic/redacted plain-text chunks。重入复用首次持久化的delete deadline；Bot明确拒绝默认同调用重试一次，再次拒绝将request终止为`failed`并要求重新发起preview。数据库、queue、audit和普通日志不保存preview正文，图片仅展示reference/hash/MIME/尺寸/detail metadata。已知Bot message ID默认十分钟后best-effort删除；delete claim先持久化lease/fencing，失败按1分钟起步、1小时封顶退避，24小时只触发一次critical alert。`send_unknown`不自动重发，删除失败写`delete_partial`并保留残余风险。Telegram通知、cache、forward、截图和未知发送可能无法擦除。

Media retention清理同样使用PostgreSQL lease/fencing：只领取到期且无`message_media`引用的对象，先提交claim再做hash-verified文件删除；崩溃后可重领，旧worker不能覆盖新claim，成功后清除path/hash，失败按1分钟至1小时退避。
