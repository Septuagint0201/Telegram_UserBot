# M2 Compatibility Set

本文固定M2模型配置、协议wire contract、credential envelope与key-only控制面的兼容边界。M2只允许synthetic fixture、local fake和disposable PostgreSQL/Redis；它不表示任何真实模型provider、Telegram Bot、Caddy或Ubuntu生产部署已验证。

## 1. 固定依赖

| 组件 | 固定版本 | M2用途 |
|---|---:|---|
| CPython | 3.14.7 | Windows本地与GitLab Linux候选解释器 |
| cryptography | 50.0.0 | AES-256-GCM、HKDF与认证失败处理 |
| httpx | 0.28.1 | ASGI contract test；M2不提供可访问公网的production provider transport |
| Starlette | 1.6.0 | key-only Web App页面、静态资源和单一credential mutation API |
| Uvicorn | 0.52.1 | loopback browser harness server |
| Playwright | 1.62.0 | dev/CI Chromium browser gate |

所有Python包均由`requirements/runtime.lock`与`requirements/dev.lock`的exact version和hash固定。Playwright在GitLab `m2-browser`作业中安装其匹配的Chromium binary；实际browser version写入`.artifacts/m2/browser-manifest.json`，不能只按driver版本推断。

M2数据库仍使用[M1 Compatibility Set](m1.md)固定的PostgreSQL 17.10/pgvector 0.8.6和Redis 8.2.8。Alembic head为`0002_m2_model_control`，必须实际验证empty→head、head→base→head和`0001_m1_durable_state`→head。

## 2. Canonical profile与协议矩阵

部署初始化四个互相独立的profile：

| Logical role | Kind | 可选协议 |
|---|---|---|
| `main_ai` | generation | `openai_responses`、`openai_chat_completions`、`anthropic_messages` |
| `memory_agent` | generation | 同上 |
| `proactive_agent` | generation | 同上 |
| `embedding` | embedding | `embedding` |

Canonical非密钥字段固定为endpoint identity、credential identity、protocol、model name、temperature、maximum output tokens、timeout、enable和typed protocol options。实际wire mapping为：

| Protocol | 路径 | 输出上限字段 | M2特有选项 |
|---|---|---|---|
| Responses | `/responses` | `max_output_tokens` | `reasoning_effort` |
| Chat Completions | `/chat/completions` | 验证时解析为`max_completion_tokens`或`max_tokens` | `token_limit_field` |
| Messages | `/messages` | `max_tokens` | `api_version`、`x_api_key/bearer`认证；路径固定 |
| Embedding | `/embeddings` | 不适用 | `dimensions`、`encoding_format`、`batch_size` |

旧式纯文本`/completions`明确不支持。M2 contract覆盖text、image `detail=auto`、structured output、stream normalization、usage、429/5xx、malformed response、timeout/cancel传播与embedding排序；不执行真实provider请求。因此这里的兼容性是仓库canonical↔wire contract，不是对任意provider/model部署的live声明。真实启用项的synthetic provider smoke留在M9并需单独授权。

## 3. 配置、credential与轮换边界

- endpoint、protocol、model和参数只通过Control Bot命令及最长15分钟的durable多步会话修改；输入是逐字段受控值，不接受任意JSON。
- `/model_validate`写入匹配endpoint/protocol/model的不可变capability snapshot；`/model_activate`在同一事务重新检查未过期snapshot、credential和profile/draft CAS，失败保留旧active config。
- config version只绑定稳定credential identity。每个新run取得active snapshot时解析当前credential version，并在run自身记录版本；替换key只影响新run，仍在恢复窗口内且未销毁的旧版本可由受限函数读取。
- API key只通过`/model_key <role> [set|replace|delete]`产生的5分钟一次性Web App launch提交。Web App没有模型配置、credential读取或状态查询API；成功仅返回空204，状态只由Bot显示。
- ciphertext使用AES-256-GCM、随机96-bit nonce、版本化master key和绑定deployment/role/profile/credential/version的AAD。日志、audit、HTTP response、Telegram消息和测试artifact不得包含明文key。
- credential删除单向清空所有版本的ciphertext、nonce和fingerprint，并禁用profile；数据库trigger禁止恢复或改写已销毁版本。

## 4. Endpoint与浏览器安全边界

公网endpoint只接受HTTPS且所有A/AAAA必须为public unicast。私有HTTP(S)只能由不可从Bot修改的root-owned policy精确限定scheme/host/port/CIDR。连接契约禁用redirect和environment proxy、要求DNS重验与已批准地址绑定；production HTTP transport在后续milestone接入时必须消费该契约，不能自行弱化。

Web App要求canonical HTTPS origin；只有browser test可显式启用loopback HTTP。POST必须同时通过same-origin检查、Telegram `initData` HMAC/管理员/5分钟时效、43字符launch proof、deployment/action/role/credential CAS和持久化rate limit。Launch与Telegram `tgWebAppData`位于URL fragment，不进入HTTP request target；页面无第三方resource、cookie、local/session storage或credential echo。
