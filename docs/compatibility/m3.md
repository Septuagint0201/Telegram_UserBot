# M3 Compatibility Set

本文固定M3 Telegram ingest、outbound identity、reconciliation与恢复边界。M3只允许synthetic fixture、deterministic Telegram fake和disposable PostgreSQL/Redis；没有使用真实Telegram Session、账号、peer或消息，真实ingest/send均为`NOT RUN`。

## Runtime与依赖

| 组件 | 固定版本 | M3用途 |
|---|---|---|
| CPython | 3.14.7 | Windows门禁与GitLab Linux执行环境 |
| Telethon | 1.44.0 | 注入client后的MTProto request adapter；不创建Session |
| PostgreSQL / pgvector | 17.10 / 0.8.6 | canonical event、revision、intent、attempt和恢复状态 |
| Redis | 8.2.8 | 沿用M1 dispatch兼容面；M3不把消息正文放入Redis |

Alembic head为`0003_m3_telegram_lifecycle`，migration链必须验证empty→head、head→base→head、`0001_m1_durable_state`→head和`0002_m2_model_control`→head。M3新增6张表：`outbound_delivery_groups`、`outbound_intents`、`outbound_attempts`、`telegram_read_states`、`telegram_typing_states`和`telegram_operations`。

## Telegram边界

`TelethonTelegramGateway`只接受composition root注入的已连接client与peer resolver；adapter不构造`TelegramClient`、不选择Session路径，也不启动连接。最终部署仍由`app`进程独占Session。默认`telegram-userbot-check`入口不实例化该adapter，不访问Telegram或读取Session。

V1 ingest只允许private、non-Bot、non-self的一对一user peer。group、channel、secret chat、Bot、self和unknown peer只保存content-free event metadata，`conversation_id`为空，不保存正文、caption、file reference或media row，也不产生模型调用。M3不实现Main AI调用，因此即使eligible private消息也不会自动生成或发送回复。

规范化事件覆盖create、edit、delete、reaction和service。事实去重使用versioned SHA-256 update fingerprint；canonical message唯一范围仍由conversation映射固定为`account_id + conversation_id + telegram_message_id`，等价映射到Message Lifecycle的`account_id + chat_id + telegram_message_id`。delete tombstone优先于迟到create/edit；正文revision只允许单向redaction。

Telegram photo和image MIME document在M3只保存受控metadata与`download_eligible=true`，不下载二进制、不创建ready media object。voice、audio、video、video note、非图片document和sticker只保存metadata并固定`download_eligible=false`。实际下载、MIME sniff、decode、pixel/byte limit与`detail=auto` provider映射属于M5。

## Outbound与恢复

任何system send必须先持久化delivery group及全部ordered intents。每个intent保存稳定、正数、non-zero的63-bit `telegram_random_id`与payload SHA-256；FloodWait和transient retry复用相同ID。每次side effect严格拆为transaction A claim并commit `started` attempt、无数据库事务的单次RPC、transaction B单向结算；遗留started attempt恢复为unknown。结果分为success、FloodWait、transient、permanent和unknown。unknown或crash-after-dispatch只进入对账，不自动回到pending，也不生成新random ID。

Observed outgoing按已映射Telegram message ID或random ID匹配intent；匹配后使用group source并结算intent，存在active sending/unknown但无法精确匹配时保持`system_pending/pending`，只有不存在system候选时才归类为human并推进`mode_version`。对账依据不会猜测未知消息来源。

M3已创建完整outbound identity、payload、状态、attempt与恢复表，并在group/intent中逐字保留`model_run_id`。M4才创建`model_runs`、turn、final send gate与splitter快照，因此M3 migration有意不添加`model_run_id`外键，也不提前声称AUTO授权。M4必须以新的Alembic migration补齐Data Model定义的composite FK、turn/model snapshot字段及终态词汇；不能通过应用层假设替代数据库约束。

Read acknowledgement port使用单调high-watermark，重复operation按32-byte idempotency key去重。Typing port提供start/refresh/stop side effect，数据库只保存短期lease token、expiry和version；由M4决定只有AUTO generation期间才调用它们。

## 证据状态

Windows当前完成Ruff、strict mypy、unit/contract/fake测试；本机没有可用Docker daemon，因此PostgreSQL migration、role、repository与recovery integration为`NOT RUN`，不能由静态检查升级为`PASS`。GitLab Linux evidence在候选签名commit推送后生成，包括migration manifest、12项content-free replay matrix和M3-001—M3-010 acceptance manifest。

真实Telegram ingest/send、Session owner运行时、真实FloodWait、provider、Ubuntu production、backup/restore、production load和24小时soak均为`NOT RUN`。M3完成不授权连接真实账号或启用自动发送。
