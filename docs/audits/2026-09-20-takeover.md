# 接手审计与隔离验证 — 2026-09-20

## 结论

第一步审计已完成。现有领域逻辑、数据模型和分层值得保留；当前主要缺口是生产后台流程尚未全部接入，不能把项目描述成“只差运行证据”，也不能据此部署为完整产品。

`docs/Design.md` 保持原样，SHA-256 为 `b09a2eb2aaeba20d77f9ebe7519a0b376e410f00032947a3c1e3738d8b4f5a7e`。其余历史计划和 M7 验收只作为参考；本报告区分当前工作树的实际行为和历史结论。本轮没有提交或部署发布版本。

## 本轮修复

1. **人工接管响应**：App 调度器独立处理控制命令，避免模型生成、Telegram 发送或媒体任务等待期间，HUMAN/暂停命令一直排队。TaskGroup 保证任一循环失败或取消时，另一循环也先退出，再报告调度器停止。已有慢生成、慢发送、慢媒体和取消测试。
2. **不支持的 Telegram peer**：允许 `message_events.conversation_id` 为空，保留账户归属和无正文事件记录；不为这类事件建立 AI 会话。迁移推进到 `0029_unsupported_peer_events`。
3. **迁移与状态写入一致**：同步服务状态投影和历史事件的版本约束、部署配置及迁移证据链。新增真实 PostgreSQL 回归覆盖从 0028 升级、升级后状态写入、保留历史的部分回滚，以及拒绝删除数据的回滚路径。
4. **旧测试数据适配当前约束**：M6 模型运行绑定实际 job/manifest；M7 待执行任务补齐会话归属，表清单包含 M8 新增表。保留生产跨账户、所有权和用途约束。
5. **恢复测试的文件权限**：在临时目录创建 root 所有的 Compose 输入，避免测试依赖源码检出目录的所有者；生产权限校验继续生效。

### 0029 回滚边界

当存在无会话归属的事件时，回退到 0028 会以 `MIGRATION_0029_DOWNGRADE_REQUIRES_SCOPED_EVENTS` 原子拒绝。迁移不会删除这些事件以强行恢复 `NOT NULL`。无此类事件时可以部分回滚；服务状态历史保留原始版本。继续回退到更早版本还受各历史迁移约束，不能由本次测试推定为可行。

## 第二步实现：持久化记忆删除队列

本轮按缺口优先级先完成删除流程中可以安全闭环的一段：

1. `DurableCompensationPublisher` 周期扫描 `requested`、`quiescing`、`redacting`、`media_cleanup` 和 `derived_cleanup` 请求，按请求 ID 幂等创建不携带正文的 `memory.reconcile_erasure` worker job，并重建对应的 durable outbox 唤醒。
2. 新执行器只接收 `request_id`，在 PostgreSQL 中重新读取请求并持有行锁；记忆范围删除会推进 logical redaction、ledger、finalize 三段 progress，使用幂等键写入 ledger，并将请求原子收敛到 `completed`。
3. 当前请求若是 contact 或 account 范围，仍会写入稳定的 `ERASURE_SCOPE_PIPELINE_UNAVAILABLE` 失败状态；系统不会把未实现的范围伪装成成功删除。重复消费、进程中断和已完成请求均可安全重放。

服务器 PostgreSQL/Redis 集成已验证这条路径：3 个 M8 worker runtime 测试全部通过，覆盖记忆删除、progress/ledger 完成、无正文入队和 outbox generation 重建。该实现只关闭了 memory scope 的删除缺口，尚未声称完整删除与异机恢复闭环已经完成。

## 第三步实现：累计 erasure ledger 导出

本轮继续完成恢复链中可以独立验收的一段：

1. `restore_gate.py --export-ledger` 使用既有 `telegram_userbot_export_runtime` 只读身份，按账号导出已完成删除请求的累计 JSONL 台账；文件只含 keyed HMAC、scope、request UUID、幂等键、策略版本和完成时间，不含账号 UUID、目标 UUID 或任何正文。
2. 导出文件使用临时文件、fsync、原子替换和固定权限写入；恢复解析器按请求幂等键允许同一目标的多次合法删除，拒绝重复请求键，并保持已导出历史不会回退。
3. Production Compose 新增 `erasure-ledger-export` ops 服务，最小化数据库列权限，并配置 systemd 每五分钟调度（尚未在生产安装启用）；输出目录与现有 export staging 使用独立的 root-owned 路径和组权限。

本地 operations 契约为 113 passed、2 skipped、1 deselected；Ubuntu 服务器临时 PostgreSQL 17/pgvector 容器中的台账权限、账号隔离、重复目标、只读事务和恢复重放测试为 2 passed。临时容器已删除并确认无残留。contact/account 请求仍保持 `ERASURE_SCOPE_PIPELINE_UNAVAILABLE`，因为本地多范围数据清理和物理媒体确认尚未接入消费者。设计要求尽力删除的外部副本是 Control Bot 预览消息；无需删除用户账号的远端聊天记录。

## 第四步实现：删除请求与 Control Bot 预览联动

1. contact/account 的持久化删除意图会阻止新建预览、消费确认令牌、重建预览正文、开始投递及领取后续分片。即使本地清理请求处于 failed，仍保持阻断；memory 范围请求不会禁用整个会话。
2. Control 维护循环按 Bot 分批撤销预览和未使用令牌，单批默认 50、最多 100，支持 SKIP LOCKED 和幂等重扫。Control 仅新增删除请求 account_id/scope_type/contact_id 和会话 id/account_id/contact_id 的范围标识读取权限。
3. 已知 Bot 消息 ID 在删除意图可见后立即可领取删除任务，无需等原来的十分钟期限或本批撤销扫描。已经开始的发送仍记录迟到结果；已知 ID 立即可删除，未知发送结果保留为 send_unknown，不会重发或虚报删除成功。
4. 继续使用已有 Bot API delete_message、租约、fencing token、失败退避和 critical 告警。预览请求标记 cancelled 表示撤销预览能力，外部清理结果仍以每条 delivery 记录为准。
5. 撤回上一增量中尚未接入的用户账号 delete_messages API 及其两项专属测试。该 API 来自对设计的错误解读，不是 contact/account 本地删除的前置条件。已有发送结果映射等改进保留，Design 文件未改动。

本地默认测试 1523 passed、3 skipped、73 deselected，覆盖率 86.97%。Ubuntu 隔离 PostgreSQL 中 12 项集成测试通过（新增 6 项预览删除场景及原有 6 项上下文/媒体回归），涵盖真实 Control 列权限、账号与 Bot 隔离、迟到结果、未知结果保留、租约及退避。临时数据库绑定随机 loopback 端口，并已删除。本轮证据位于 `.artifacts/preview-erasure-20260922/`，包括原始测试日志、JUnit、源码哈希及初次失败记录。测试期间修正了旧 editable 环境加载、样本指纹/策略唯一性及 Control 归属列权限问题。该步骤关闭预览撤销与外部已知副本清理的联动缺口，尚未完成 contact/account 本地数据清理、物理媒体确认、off-host 台账复制或真实 Telegram 验证。

## 第五步实现：contact/account 派生正文与快照清理

2026-09-28 后续增量接入了派生数据清理，不再停在 `ERASURE_DERIVED_CLEANUP_PENDING`：

1. 在同一删除事务中清空记忆及其历史版本、候选 proposal、摘要、COPILOT revision、outbound 正文、模型输入/输出哈希、上下文与记忆 manifest 哈希，以及主动联系来源 payload、证据摘要和决策快照。关联 embedding 行实际删除。
2. 递归追踪记忆/摘要证据依赖，并清理引用这些来源的 manifest 及关联模型/输出。其他会话中受污染的派生内容也会清空，无关 canonical 消息保留。待发意图取消，sending/sent/unknown 的外部结果、random ID、租约和历史继续保留；准确的迟到回执仍可结算。

## 第六步实现：导出撤销、物理清理与预算结算

2026-09-28 新增 `0031_scope_export_budget`。Contact/account 删除意图在数据库事务内立即撤销重叠的导出：联系人删除同时覆盖整账号导出，保留其他联系人的独立导出及其他账号。旧请求在迁移时补齐撤销标记；新导出、重新领取和迟到完成均受数据库限制。导出进程与清理进程使用持久的请求级文件锁，领取后先重新验证租约，再读取或写出文件。清理涵盖已登记文件、崩溃遗留的未登记文件、历史尝试及加密临时文件；已登记文件校验摘要，拒绝符号链接和异常文件，文件删除确认后才写 `erasure_cleaned_at`。Worker 只有这些导出记录的读取权限，不能代替文件持有者宣称清理完成。

删除流程已接入保守预算结算：无发送副作用且目标已终止的 held 预留释放；已完整发送的记账 committed；已开始发送但结果不确定或部分发送的记账 send_unknown；证据不足的继续 held 并报告 `ERASURE_BUDGET_PENDING`。结算与三个适用预算桶共用事务，重复执行不重复退还或扣费。新增授权及重新绑定也受删除意图限制。此前 `ERASURE_FINALIZATION_PENDING` 请求恢复执行这两步；最终仍停在 `ERASURE_METADATA_PENDING`，不生成完成台账。

另修正 data-export Compose 定时入口缺少参数的问题：默认 `--maintenance` 先清理、再领取一个导出。日常窗口外可使用 runbook 的 `--cleanup-due` 命令加速删除。升级前需要停止旧版本导出/清理进程，并使用配套迁移、角色脚本和镜像；旧进程没有新文件锁协议。

## 第七步实现：资料与运维元数据清理

## 第八步实现：共享媒体及遗留上传恢复

2026-09-28 新增 `0033_media_upload_erasure`，接入可恢复的上传文件清理：

1. 上传在写文件前记录 `source_revision_id`，原图和 provider copy 绑定相同来源与账号；即使未完成最终附件关联，范围删除也能发现它们。数据库阻止删除意图之后的新上传、给正在删除的对象追加引用、改写来源或复活已删除对象。
2. 共享媒体按原图/provider family 判断仍有效的引用。其他联系人仍有有效引用时继续保留，但不再阻塞同一请求中的独占媒体；最后一个引用被清理或普通保留期到期后，原请求可以继续推进。已经 redacted 的历史引用和已删除对象不会造成永久等待。
3. Pending、rejected 和旧 failed 上传超过五分钟进入物理检查；有明确来源的删除请求可立即推进。没有来源绑定的旧上传使联系人请求保留 `ERASURE_MEDIA_UNATTRIBUTED_UPLOAD`，不能跳过文件检查直接确认完成。
4. 文件写入与清理使用同一跨进程锁。清理先持久化对象删除标记，再检查已登记摘要及同一 UUID 的未登记文件、临时文件；迟到写入检查标记后拒绝恢复文件。文件删除后、数据库确认前中断，可在租约到期后重新确认不存在。符号链接、异常文件和摘要变化均保留失败状态。
5. 匿名旧 `.ingest-*` 文件无法安全归属联系人，保留待处理；已进入 deleting 的整账号清理会先禁止该账号所有写入，再清除此类遗留文件。App 定期清理限定到其配置账号。Worker 仍只能请求清理；旧 failed 状态由数据库受限转换为可清理状态，不授予 Worker 宣称文件已删除的权限。
